## Context

Мотивация и объём — в `proposal.md`. Тема сейчас использует стандартные `darkColorScheme()`/`lightColorScheme()`. `UiNodeContent.kt` выводит весь серверный текст цветом `primary`, создаёт обычный `TextField` и отправляет его локальное значение по аппаратному Enter. Микрофон — отдельный соседний `voice_input`; сервер задаёт строку с весами `[1, 0]`. `MainActivity.kt` уже содержит `TopAppBar` с названием и Refresh.

Дизайн нужен для согласованного изменения темы, рендерера и оболочки, а также выбора места кнопки отправки без расширения JSON-контракта.

## Goals / Non-Goals

**Goals:** использовать существующие Material 3 компоненты и локальное состояние поля; сохранить серверную композицию TEA и непрозрачные события.

**Non-Goals:** распознавать смысл узлов по тексту label или event, вводить универсальный style-объект в протокол либо собирать новый клиентский экран вместо серверного дерева.

## Decisions

### 1. Палитра через существующую тему

Задать в тёмной схеме фон `#14171C`, поверхности контролов `#1D222A`, primary `#82AAFF`, светлый `onSurface`/`onBackground` (ориентир `#E6EAF0`) и тёмный `onPrimary`, чтобы текст и иконки на синей заливке читались. Обычный серверный текст использует `onSurface`. Системный выбор темы и штатная светлая схема сохраняются: это минимальный вариант без нового переключателя и настроек. Принудительно тёмный режим не нужен для переноса тёмного варианта макета.

### 2. Оформление в конкретных компонентах

Сохранить `TopAppBar`, визуально согласовав его с фоном; сохранить текстовый Refresh. Увеличить внешний горизонтальный отступ с 4 до 12 dp. Не увеличивать автоматически все вложенные промежутки: дерево содержит служебные вложенные column/row, и накопленные отступы отнимут место у чата. Для поля использовать существующий `TextField` с радиусом 16 dp, поверхностью из темы и без стандартного нижнего подчёркивания. Уточнения визуальных величин при проверке допустимы в пределах этой структуры.

Не вводить роли заголовка/вторичного текста в протокол ради первой итерации. Не пытаться определить нужный стиль по строкам `OpenCode session`, `Prompt` или форме backend event.

### 3. Стрелка принадлежит input

Разместить стандартную иконку стрелки вверх в `trailingIcon` существующего поля. Использовать небольшой Android vector drawable без новой зависимости (библиотеки Compose-иконок в проекте нет), доступное описание действия и цель касания минимум 48 dp. Нажатие вызывает тот же `onInputEvent(node.event, value)`, что Enter, и учитывает `eventInProgress`.

Применять это к каждому `input`, включая Branch: все такие узлы уже означают отправку собственного значения. Отдельная серверная кнопка не подходит, поскольку её событие не содержит текущий локальный draft. Специальный prompt-компонент или форма с несколькими полями здесь не нужны.

Микрофон остаётся отдельным узлом справа от поля и только заполняет его. Не объединять его локальное состояние с input и не менять правила распознавания. Текст продолжает храниться и сбрасываться по существующим правилам `LocalUiDocument`; кнопка не очищает его самостоятельно.

## Risks / Trade-offs

### Подтверждённое расширение: переполнение кнопок

Визуальная проверка при ширине 800 px (400 dp) выявила, что первый элемент обычного `row` занимает почти всю ширину, а следующие кнопки переносят подписи по буквам и становятся очень высокими. Это происходит в серверных композициях Emulator и Worktree shortcuts. Пользователь разрешил включить исправление в этот change.

Использовать существующий `column ~stretch:true` для группы Worktree shortcuts: каждая кнопка получает всю ширину своей панели, порядок и события сохраняются. Вертикальная компоновка одинакова на широких и узких экранах. По последующему прямому указанию пользователя Emulator возвращён к исходному `row`; исправление переполнения этой группы исключено из change. Рендерер row и JSON-протокол сохраняются.

- Дополнительные 48 dp у поля уменьшают место для текста в узкой левой панели → проверить реальную узкую ширину, длинный prompt и открытие клавиатуры; сохранить однострочное горизонтальное прокручивание поля и доступность кнопок.
- Некоторые Material-компоненты используют отдельные цвета контейнеров → проверить шапку, поле и кнопки в обеих темах, а не считать изменения `background` достаточными.
- Изменение общего input затрагивает Branch, Commands и Prompt → проверить отправку текущего текста общим тестом рендерера и осмотреть эти экраны.
- Макет содержит много свободного места → переносить палитру и форму контролов, а не его абсолютные размеры, чтобы сохранить рабочую область чата.

## Migration Plan

Палитра и отправка поставляются Android-сборкой, совместимой с существующим backend. Вертикальные группы кнопок поставляются обновлением backend и используют уже поддерживаемые узлы. Миграции данных не требуются; клиент и backend можно откатывать независимо. Проверки перечислены в `tasks.md`.
