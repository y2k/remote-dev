## Context

См. `proposal.md`. Сейчас `Cmd` представляет отложенную функцию `unit -> 'msg option`, но `Worktrees.update` возвращает навигацию отдельным optional `Route`. `Home.update_page` применяет этот маршрут синхронно, а `dispatch` записывает модель, запускает `Cmd` и рекурсивно обрабатывает его message. Сервер обрабатывает текущую модель синхронно; рефакторинг не добавляет асинхронность и не меняет JSON-протокол.

## Goals / Non-Goals

**Goals:**

- Сделать `Cmd` единственным результатом page `update`, не меняя его тип.
- Сохранить типизированное поднятие page commands в `Home.msg`.
- Централизовать переходы в `Home`, доставляя навигационные сообщения существующим `dispatch`.

**Non-Goals:**

- Стек экранов, сохранение модели списка при возврате или иной history API.
- Пакетирование, отмена, параллельное выполнение или асинхронное планирование commands.
- Расширение `Cmd`, OCaml effects, free monad, отдельная библиотека навигации или изменения Android-клиента.

## Decisions

### Оставить `Cmd` без изменений

`Cmd.t` сохраняет тип `unit -> 'msg option`. `Cmd.none` остаётся отсутствием действия, а навигация возвращается той же формой команды: `fun () -> Some message`. Новый type, варианты результата и helper для отправки message не нужны.

Каждая page `update` возвращает пару модели и `Cmd.t`. `Cmd.map` продолжает поднимать только page messages в `Home.msg`; отдельного `Effect.map` нет.

Альтернатива с `Effect` отклонена: `No_effect` повторяет `Cmd.none`, а `Command` и его mapping повторяют существующий `Cmd`. Альтернатива с расширением результата `Cmd` вариантами message и navigation отклонена: для доставки навигации достаточно уже существующего message.

### Доставлять navigation как внутренние messages

`Worktrees.Select path` очищает ошибку и возвращает `Cmd`, который доставляет внутреннее page message для открытия path. `Home` поднимает его существующим `Cmd.map`, распознаёт его только при активном списке и входит в выбранный worktree.

`Home.Back` возвращает `Cmd` с отдельным внутренним message применения возврата. `Home` обрабатывает его по активному экрану: из worktree входит в новый список и запускает его загрузку, а на корневом списке не меняет состояние. `Route.t` удалить.

Альтернатива с прямым созданием `Home.msg` дочерней страницей отклонена: она создаёт обратную зависимость. Альтернатива с сохранением `Route` как третьего результата отклонена: она оставляет второй канал для navigation.

### Сохранить текущий runner `dispatch`

После каждого `Home.update` существующий `dispatch` сначала сохраняет state в `Atomic`, затем запускает `Cmd` и передаёт возвращённое message в следующий `Home.update`. Поэтому выбор и возврат проходят ту же последовательность, что загрузка списка и запуск Claude; отдельный runner не вводится.

Это сохраняет порядок текущей реализации: промежуточная модель установлена до navigation message. Один `Cmd` за update достаточен; `Batch` не вводится без реального сценария.

## Risks / Trade-offs

- [Navigation требует дополнительного синхронного шага dispatch] → HTTP response по-прежнему строится после обработки command, поэтому документ и порядок записи модели не меняются.
- [Внутреннее page message может прийти на другой экран] → обрабатывать его только в паре с соответствующим активным экраном; несовпавшая пара остаётся защитным no-op.
- [Поведение `Back` может случайно стать stack pop] → явно проверить создание и загрузку нового worktree list, а также root no-op.

## Migration Plan

Изменение не требует миграции данных или развёртывания. Проверить форматирование, сборку и текущие HTTP-level тесты; откат состоит в восстановлении отдельного `Route` результата.
