## Context

Мотивация — в `proposal.md`. `lib/components.ml` содержит варианты `Column`/`Row`, функции композиции, рекурсивный `map` и JSON-сериализацию. В Android модель и общий разбор контейнеров находятся в `MainActivity.kt`, отрисовка — в `UiNodeContent.kt`. Текущие контейнеры не рисуют фон; `Theme.kt` уже содержит все пять выбранных ролей. Изменение пересекает backend, протокол и клиент, поэтому нужен общий дизайн.

## Goals / Non-Goals

**Goals:** расширить существующий путь серверной композиции небольшим типизированным параметром и использовать текущую тему непосредственно при отрисовке.

**Non-Goals:** универсальный объект стилей, произвольные RGB-цвета, дополнительные роли, новые обёртки компоновки или автоматический выбор цвета содержимого.

## Decisions

### 1. Закрытый набор ролей в существующем API

Добавить в `Components` тип `theme_color` с вариантами `Background`, `Surface`, `Surface_container`, `Primary`, `Primary_container`. Функции `row` и `column` получают необязательный `?background`; соответствующие варианты дерева хранят `theme_color option`. Например: `column ~background:Surface children`.

Рекурсивный `map` сохраняет фон. Сериализация преобразует роли в согласованные camelCase-строки и опускает поле при `None`. Закрытый тип предпочтительнее произвольной строки: backend не может случайно отправить опечатку. Существующие сопоставления с вариантами дерева, в том числе в тестах, обновляются под новый аргумент; отдельный style-слой не нужен.

### 2. Разбирать роль, разрешать цвет при отрисовке

В Android использовать небольшой enum для тех же пяти ролей и nullable-поле с default `null` у обоих контейнеров. В общей ветке парсера разбирать `background` один раз. Отсутствующее поле означает отсутствие заливки; неизвестная строка или иной тип, включая null, даёт существующую ошибку разбора. Строгость соответствует уже принятой обработке `stretch` и `weights`.

При отрисовке простое сопоставление роли выбирает свойство `MaterialTheme.colorScheme`. Не сохранять конкретный цвет в разобранном документе: один документ должен корректно отображаться в обеих темах. Не добавлять реестр ролей, рефлексию или зависимости.

### 3. Только Modifier.background

Применить стандартную заливку к текущим `Row` и `Column` вместе с существующими модификаторами размеров. Не добавлять `Surface`: он может менять цвет содержимого, тогда как пользователь согласовал только фон. Само свойство `background` не добавляет padding, скругление или принудительное заполнение свободного места. Заливка покрывает фактические границы контейнера и промежутки между детьми; при отсутствии роли модификатор заливки не нужен.

Цвета `Text`, кнопок и input остаются текущими. Вложенный контейнер без фона прозрачен, с фоном — рисует собственную заливку.

### 4. Применение к полной панели Emulators

Задать `~background:Surface` внешней колонке `Emulator.view` в `lib/home_components.ml`, которая объединяет ошибки и содержимое панели. Это покрывает также состояния без выбранного устройства и без запущенных эмуляторов. Роль `surface` соответствует поверхности правой панели в согласованном макете; в тёмной теме она уже равна `#1D222A`.

Для заполнения высоты использовать существующий `~weights:[0; 0]` у этой колонки: рендерер любой weighted-column уже вызывает `fillMaxHeight`, а нулевые веса сохраняют высоту содержимого обоих детей и не создают новых прокручиваемых областей. Свободное место снизу остаётся частью окрашенной колонки. Полная ширина правой доли уже передаётся из корневого `row ~weights:[2; 1]` через `Box` с `propagateMinConstraints`; `stretch` для потомков не нужен. `MainActivity` предоставляет ограниченную высоту области содержимого. Новое свойство высоты и специальное распознавание панели на клиенте не нужны.

Проверить заливку до нижней границы доступной области на коротком содержимом и при показе превью. Фон не перекрывает шапку и внешние отступы, не меняет пиксели скриншота, его пропорции и обработку нажатий. Контролы остаются в существующем порядке и горизонтальном ряду; отношение ширин панелей остаётся 2:1.

## Risks / Trade-offs

- На `primary` существующий `onSurface` может иметь слабый контраст → фон и содержимое намеренно независимы по решению пользователя; автоматическую смену текста не вводить.
- В тёмной палитре `surface`, `surfaceContainer` и `primaryContainer` сейчас совпадают → проверять разрешение ролей по значениям темы, а не ожидать пяти различных оттенков.
- Ошибка размещения заливки может нарушить границы или прокрутку → использовать существующие контейнеры и проверить обычный, weighted и stretch-варианты в текущих Compose-тестах.

## Migration Plan

Сначала поставить клиент с поддержкой поля, затем backend с обновлённой композицией Emulators. Документы без поля совместимы с новым клиентом; текущий старый парсер игнорирует неизвестное поле, поэтому на нём новая заливка просто не появится, а уже поддерживаемые веса заполнят высоту панели. Для возврата прежнего оформления убрать фон и новые веса внешней колонки Emulators. Миграции данных нет.
