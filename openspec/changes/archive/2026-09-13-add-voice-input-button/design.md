## Context

Мотивация описана в `proposal.md`. `Components.t`, `map` и `to_json` задают серверный UI; Android разбирает его в `UiNode` и отображает через `UiNodeContent`. Уже существует маршрут `(UiEvent, String)` → `eventRequest` → `POST /`. На проводе `event` — JSON-массив, несмотря на устаревшие упоминания объекта в части основной спецификации. Новый элемент использует фактический массив без изменения старых элементов.

Manifest пока не объявляет `RECORD_AUDIO`. Реализации записи и распознавания в текущем Android-клиенте нет. Доступ к оригиналу получен; изучены `client/app/src/main/java/io/y2k/remote_android/widget/input/view/component/SpeechInput.kt`, соседний `ChatInput.kt`, `client/app/src/main/AndroidManifest.xml`, `client/app/build.gradle.kts` и `client/design-system/src/main/java/com/example/remoteandroid/designsystem/Theme.kt` в `~/Projects/remote_android_development`. Исследование выполнено чтением исходников, без проверки на устройстве.

## Goals / Non-Goals

**Goals:** самостоятельный переиспользуемый компонент с минимальным контрактом; использование имеющегося транспорта; локальное управление микрофоном и жизненным циклом.

**Non-Goals:** автоматическая отправка распознанного промпта агенту, настройка подписи/иконки, универсальный интерфейс нескольких движков распознавания, новый транспорт событий.

## Decisions

### 1. Отдельный примитив с фиксированным видом

Добавить `voice_input` с обязательным `event`-массивом. Конструктор OCaml и модель Android не принимают `label` или `text`; переданные в JSON поля `label`/`text` отклоняются, чтобы текст нельзя было задать и через wire-контракт. Это предпочтительнее режима обычной кнопки, поскольку удержание и асинхронный результат имеют другой жизненный цикл.

Android-реализацию разместить в отдельном `VoiceInputButton.kt`; в `UiNodeContent` оставить подключение. Взять из оригинала размер 48 × 48 dp, скругление 12 dp, отступ 12 dp и системную иконку `android.R.drawable.ic_btn_speak_now`; цвета взять из текущей темы без переноса дизайн-системы. Сохранить внутреннее accessibility-описание, подсветку записи и добавить индикатор ожидания результата. В оригинале отдельного индикатора распознавания нет.

### 2. Результат использует существующий канал

Компонент получает callback результата; адаптер узла передаёт исходный `event` и окончательный текст через имеющийся `onInputEvent`. Компонент не знает о чате или командах агента. Backend-композиция и обработка результата остаются в TEA (`model`, `msg`, чистый `view`, `update`); локальные pointer/microphone-состояния не требуют серверных событий на каждый переход.

В `Worktree.view` и `Session.view` заменить одиночный input строкой `row ~weights:[1; 0]`: input слева занимает оставшуюся ширину, микрофон справа сохраняет размер 48 dp. Событие микрофона — `Set_prompt "__VALUE__"`; в Worktree переиспользовать существующий обработчик, в Session добавить аналогичный вариант сообщения и чистое обновление `prompt` с `Cmd.none`. Результат заменяет весь текст поля, не дописывает к нему. Новый UI-документ передаёт значение через существующий `edit ~text:prompt`; Enter по-прежнему отправляет `Run_prompt` с текущим, в том числе отредактированным, текстом. Голосовое событие не должно вызывать запуск CLI или отправку промпта в OpenCode.

Android сейчас хранит ввод через `remember(node)`. Проверить не только изменившийся серверный prompt, но и повторный такой же результат после локального редактирования: если сервер возвращает равный прежнему узел, локальный текст всё равно должен замениться голосовым результатом. При необходимости сбрасывать состояние input при принятом новом UI-документе через идентичность документа; не вводить адресацию соседних полей в универсальный голосовой компонент. Сохранять локальный ввод до успешного ответа и при ошибке запроса.

```text
Idle --press--> Listening --release--> AwaitingResult --final--> emit
                  |
                  +--early final--> AwaitingRelease --release--> emit
```

Отпускание вызывает `stopListening()`, если захват ещё активен, но не обещает синхронный результат. Системный сервис может сам завершить фразу до отпускания. Первый окончательный результат сохраняется до отпускания либо отправляется сразу, если палец уже отпущен. Отправка выполняется один раз после обоих условий: получен непустой окончательный текст и завершено удержание. Промежуточные результаты игнорируются, раннее завершение не запускает новую сессию автоматически. Отмена на любом этапе, включая ожидание отпускания с готовым текстом, удаляет результат без отправки.

### 3. Минимальные правила жизненного цикла

Предлагаемые defaults для реализации: отмена жеста, уход приложения в фон или удаление/замена компонента прекращают текущую операцию; поздний результат не отправляется в другой экран. При отсутствии разрешения запросить его; после выдачи разрешения требовать новое удержание, чтобы запись не началась после отпускания пальца в системном диалоге. Ошибка или пустой результат не создают backend-события; ошибка доступна пользователю вне подписи кнопки.

Повторная запись недоступна до завершения текущей голосовой операции и во время backend-запроса. Если другой backend-запрос начался во время голосовой операции, отменить её и не ставить результат в очередь: существующий транспорт сериализует события и не имеет очереди.

### 4. Штатный распознаватель из оригинала

Использовать `SpeechRecognizer.createSpeechRecognizer` и `RecognizerIntent` с `LANGUAGE_MODEL_FREE_FORM` и `ru-RU`. Из `RESULTS_RECOGNITION` брать первый вариант, как в оригинале. Частичные результаты не нужны. Проверять доступность системного сервиса; при его отсутствии кнопка недоступна. Объявить `RECORD_AUDIO` и `<queries>` для `android.speech.RecognitionService`, запросить runtime-разрешение перед первым использованием.

Оригинал вызывает `startListening` на `ACTION_DOWN`, `stopListening` на `ACTION_UP`, `cancel` на `ACTION_CANCEL`; при pause/dispose запрещает поздние callbacks и вызывает `cancel`/`destroy`. Его `onResult` заполняет draft через `inputChanged`, поэтому переносится только механизм распознавания и оформление: новый callback отправляет backend-событие. Не переносить `taskId`, `activeTurnId`, reframe и дизайн-систему. Использовать существующие lifecycle-средства проекта для очистки вместо копирования зависимостей оригинала.

Выбран простой вариант без непрерывного захвата и повторного запуска на паузах. В реализации оставить комментарий `ponytail: системный распознаватель может завершить фразу на паузе; перейти к непрерывному захвату, если потребуется запись всей речи до отпускания`. Отдельный speech SDK, собственный сервер и ключи не требуются. Работа без сети не гарантируется: это свойство установленного Android-сервиса, а не приложения.

## Risks / Trade-offs

- Сервис может завершить фразу на паузе → принимаем это ограничение; ранний результат удерживается до отпускания, непрерывная запись отложена до реальной необходимости.
- На устройстве может отсутствовать сервис распознавания или требоваться сеть → проверять доступность, блокировать кнопку без сервиса и показывать ошибки распознавания; собственный fallback не добавлять.
- Поздний callback после навигации → отмена операции и проверка актуальности перед отправкой.
- Очень короткое удержание или тишина → завершение без события при пустом результате.
- Маленькая иконка затрудняет нажатие → стандартная область касания и accessibility-семантика; доступный способ начала/завершения записи проверить при реализации.
- Старый клиент не знает `voice_input` → сначала обновить клиент; backend не должен выдавать узел старой сборке.

## Migration Plan

Добавить поддержку узла на обеих сторонах, разместить его справа от полей `Commands` и `Prompt` и выполнить проверки, включая окончательный результат до и после отпускания и заполнение полей без отправки агенту. Откат — прекратить выдачу нового узла и вернуть предыдущую сборку; миграция данных не нужна.
