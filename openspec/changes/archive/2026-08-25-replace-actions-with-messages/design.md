## Context

См. мотивацию в `proposal.md`. Сейчас `Components.t` параметризуется отдельным `action` каждого экрана, затем `Home.event` оборачивает action для сериализации. После HTTP-декодирования те же пользовательские намерения преобразуются в отдельные `msg`; при этом результаты загрузки и streaming существуют только как `msg`.

## Goals / Non-Goals

**Goals:**

- Сделать `msg` единственным типом событий на уровне экранов и `Home`.
- Сохранить байт-в-байт JSON event objects и текущие переходы/ошибки.
- Удалить промежуточные action-варианты и `Home.event`.

**Non-Goals:**

- Не менять `Components`, request envelope, Android-клиент или обработку Claude stream.
- Не добавлять новый общий фреймворк сообщений или абстракцию событий.

## Decisions

### View создаёт `msg`

`Worktrees.view`, `New_worktree.view` и `Worktree.view` будут возвращать `msg Components.t`; `Home.view` будет возвращать `Home.msg Components.t` через уже существующий `Components.map`. `Home.to_json` будет сериализовать `Home.msg` напрямую.

Это удаляет один тип и один слой обёрток на каждом пути UI-события. Альтернатива оставить `Home.event` после удаления локальных `action` сохраняет тот же промежуточный слой и не выполняет требование использовать `msg` везде.

### Сообщение хранит ввод, доступный после HTTP-декодирования

Для input-событий вариант `msg` будет допускать отсутствующее строковое значение при рендере и декодированное значение при обработке запроса. View создаёт вариант без значения, encoder сохраняет существующий event object, а decoder добавляет `request.value`. `update` сохраняет нынешнюю реакцию на отсутствующее значение как ошибку.

Это нужно для `New_worktree` и запуска Claude: текст input существует на клиенте только в следующем запросе. Альтернатива передавать фиктивную строку смешивает UI-маркер с пользовательскими данными и скрывает отсутствие значения.

### Только UI-доступные `msg` сериализуются

Encoder каждого экрана будет сопоставлять только варианты, которые его view может поместить в `Components.t`. Внутренние варианты (`Loaded`, `Output`, `Finished`, `Error`) не получают event object и не должны попадать в дерево UI.

Это ослабляет статическое разделение, которое сейчас обеспечивает `action`, но является прямым следствием выбранного упрощения. Неподдерживаемый вариант в encoder должен завершаться немедленно, а не генерировать ложное клиентское событие. Альтернатива ввести второй тип «сериализуемых сообщений» фактически возвращает `action` под другим именем.

### Навигация обрабатывается напрямую в `Home.update`

Сообщения выбора worktree и открытия формы будут перехватываться `Home.update` до делегирования экрану. Промежуточное `Open_worktree`, генерируемое сейчас из `Worktrees.update`, будет удалено как лишнее внутреннее сообщение.

Это сохраняет переходы экранов и уменьшает количество сообщений. Альтернатива оставить двухшаговую цепочку не даёт преимущества после объединения типов.

## Risks / Trade-offs

- [Внутренний `msg` ошибочно попадает в renderer] → encoder завершится немедленно; проверка JSON всех трёх экранов подтверждает, что view создаёт только сериализуемые варианты.
- [Изменён event object нарушает Android-клиент] → проверка сохраняет прежние `type`, `path` и `prompt`, а также envelope с `value`.
- [Отсутствующий input перестанет быть ошибкой] → отдельные сценарии декодирования без `value` сохраняют текущий error state.
