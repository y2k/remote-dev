## Context

Мотивация — в `proposal.md`. `lib/components.ml` содержит типы контейнеров, конструкторы, рекурсивный `map` и сериализацию. `MainActivity.kt` разбирает оба вида контейнеров общей веткой и строго проверяет `weights`, `stretch`, `background`. `UiNodeContent.kt` использует `Arrangement.spacedBy(4.dp)`, существующие weighted/scrollable `Box` и модификатор фоновой заливки. Внешние 12 dp экрана не являются padding серверных контейнеров.

Дизайн нужен для согласования OCaml/JSON/Android и отрисовки полос без вмешательства в измерение детей. Существующая спецификация фона требует, чтобы само добавление `background` не меняло раскладку; новые отдельные атрибуты этому не противоречат.

## Goals / Non-Goals

**Goals:** сохранить стандартное измерение Compose, исходную индексацию детей и чистую серверную композицию; иметь по одному внутреннему типу и JSON-представлению для padding и gap.

**Non-Goals:** универсальная система стилей или модификаторов в протоколе, наследование spacing, настройка экранов помимо согласованного общего разделителя, произвольные цвета, новый layout engine и отдельные интерактивные узлы-разделители.

## Decisions

### 1. Небольшие типы и хелперы в Components

Разместить `Padding` и `Gap` рядом с существующими типами в `lib/components.ml`. Padding хранит `start`, `top`, `end_`, `bottom`; gap — `size` и необязательный существующий `theme_color`. Добавить `?padding` и `?gap` к `column`/`row`, сохранить их через `map`. Новые аргументы не меняют существующие вызовы конструкторов; прямые сопоставления вариантов в тестах нужно обновить.

Предлагаемый API:

```ocaml
Padding.all 12
Padding.symmetric ~horizontal:16 ~vertical:8
Padding.only ~start:16 ~top:8 ~end_:4 ~bottom:12 ()
Padding.only ~top:8 ()
Gap.make 8
Gap.make ~color:Primary 8
column ~padding:(Padding.all 12) ~gap:(Gap.make ~color:Primary 8) children
```

У `symmetric` обе оси обязательны; у `only` все стороны необязательны и равны нулю. Хелперы проверяют допустимый диапазон. Функции возвращают данные, а не дополнительные контейнеры. Альтернатива с несколькими видами padding в JSON отвергнута: нормализация нужна только один раз на backend.

### 2. Один строгий wire-формат

```json
{
  "@type": "column",
  "background": "surface",
  "padding": {"start": 16, "top": 8, "end": 4, "bottom": 12},
  "gap": {"size": 8, "color": "primary"},
  "children": []
}
```

Сериализовать padding со всеми сторонами; у gap всегда передавать size и опускать color при отсутствии. Неуказанные настройки опускать целиком, в том числе для сохранения текущих тестов точного JSON. Явно заданные нулевые значения сохранять.

Техническое уточнение диапазона: целые JSON-значения 0..2147483647 соответствуют Android `Int`; не допускать переполнения или молчаливого округления через `getInt`. Проверять исходные числовые значения до преобразования, дробные типы и строки не приводить к целым. Парсер использует нулевой padding и прозрачный gap 4 при отсутствии объекта, но не при явном null или неполном объекте. Цвет gap использует тот же `ThemeColor`, что background; согласованное расширение добавляет шестую роль `outlineVariant` в оба свойства. RGB в протокол не добавляется.

### 3. Нативное измерение, отдельная заливка gap

Оставить `Row`/`Column`, существующие weights и scrolling. Заменить константу в `Arrangement.spacedBy` на size. Порядок модификаторов контейнера:

```text
existing size modifiers --> background --> padding --> gap drawing --> children
```

Padding использовать с логическими start/end. Фон рисуется по внешним границам, а цвет gap — во внутренней области. Это сохраняет фон padding и ограничивает `stretch` внутренней шириной. Пространство для weights автоматически уменьшается на padding и промежутки.

Для цветного gap наблюдать выделенные границы непосредственных layout-детей и рисовать прямоугольники через `drawBehind`. Использовать `onPlaced`, преобразование позиции через `LayoutCoordinates.localPositionOf` в систему внутреннего контейнера и размер ребёнка. `localBoundingBoxOf` теряет положение нулевых размеров, что воспроизведено на тесной раскладке. Проходной `layout`-модификатор сохраняет измерение с исходными constraints и выделенный размер Placeable: минимальная область касания кнопки может выходить за него, но не должна менять границы gap. Это не добавляет UI-узлов и не заменяет алгоритм Row/Column. Наблюдать именно существующий weighted/scrollable `Box`, когда он представляет ребёнка, а не прокручиваемое содержимое внутри него. Для обычных детей передавать служебный Compose modifier к корневому layout-элементу; это внутренняя plumbing рендерера, не новый серверный атрибут.

У column полоса лежит между нижней границей предыдущего ребёнка и верхней следующего, на всю внутреннюю ширину. У row учитывать физический порядок в LTR/RTL: полоса лежит между обращёнными друг к другу краями соседей, на всю внутреннюю высоту. Рисовать только положительный интервал, ограниченный внутренними границами контейнера. Размер полосы определяется фактической раскладкой, которая может сжать промежуток при тесных ограничениях.

Координаты — локальные данные текущей раскладки. При изменении дерева/числа детей/направления сбрасывать устаревшие записи; обновления геометрии должны инвалидировать отрисовку, но не управлять измерением. Прозрачный или нулевой gap не требует сбора координат и рисования. Разрешение тематического цвета выполняется в composable-контексте; draw-фаза использует актуальный Color.

Отклонённые варианты: `spacedBy` самостоятельно не умеет цвет; вставленные `Spacer.fillMaxHeight()` в content-sized row способны растянуть его высоту, а аналоги для column — ширину. Intrinsic-измерение добавляет измерительную сложность для weighted/scrollable деревьев. Собственная реализация Row/Column дублировала бы готовые правила весов и ограничений.

### 4. Проверки в существующих тестах

В `test/test_remote_dev.ml` проверить хелперы, валидацию размеров, точный JSON, отсутствие новых полей по умолчанию и сохранение атрибутов при вложенном `map`. В `BackendUiParserTest.kt` расширить существующий подход к строгому разбору background и проверкам геометрии/пикселей контейнера: обе ориентации, асимметричный padding, цвет на фоне, LTR/RTL, веса/stretch/scroll, обновления дерева и смена темы. Особенно важно сравнить размеры прозрачного и цветного gap при разных размерах детей.

### 5. Согласованное расширение: разделитель панелей

Добавить `Outline_variant` к OCaml `theme_color` и `OutlineVariant` к Android `ThemeColor`. Разрешать `outlineVariant` и в background, и в gap через общий существующий код. В тёмной палитре задать `outlineVariant = #343A43`, согласованный пользователем как близкий к изображению; светлая палитра использует штатное значение Material. В общей строке `Home.view` задать `~gap:(Gap.make ~color:Outline_variant 1)`. Так все экраны с эмулятором, включая список сессий и чат, получают один вертикальный разделитель по доступной высоте без нового вида UI-узла. Соотношение панелей 2:1 применяется к ширине, оставшейся после 1 dp.

## Risks / Trade-offs

- Координаты не в той системе или наблюдение внутреннего scroll-content → преобразовывать в систему внутреннего контейнера и проверять позицию полосы при padding и прокрутке.
- Устаревшая геометрия после замены streamed-документа → привязать записи к текущему набору детей, инвалидировать отрисовку при layout-изменениях; проверить уменьшение числа детей и изменение размеров без смены числа.
- Дополнительная работа O(n) для цветных gap → один проход по соседям; без наблюдения геометрии у прозрачных gap. Кэш или отдельный layout engine не нужны.
- Цвет роли может сливаться с фоном → это ожидаемо: одинаковые роли дают одинаковый цвет, автоматическая коррекция контраста не вводится.

## Migration Plan

Сначала обновить Android-клиент, затем backend API и общий разделитель `Home.view`. Старые документы сохраняют вид. Текущий старый парсер игнорирует незнакомый gap и не отобразит его; промежуточный клиент со spacing, но без `outlineVariant`, отклонит новую роль, поэтому клиент обновляется первым. Откат backend возвращает прежние документы; миграций данных нет.
