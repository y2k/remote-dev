## Context

См. мотивацию в `proposal.md`. `Cmd` определён внутри `Home`, а `Worktrees`, `New_worktree` и `Worktree` находятся в том же файле, хотя являются самостоятельными Elm-компонентами со своими `model`, `msg`, `view`, `enter` и `update`. Из-за вложенного расположения компонент нельзя перенести как есть: внешний модуль не сможет зависеть от `Home.Cmd` без циклической зависимости.

## Goals / Non-Goals

**Goals:**

- Сделать Elm-примитивы доступными как `Components.Cmd`.
- Собрать текущие экранные компоненты в `Home_components` без зависимости на `Home`.
- Сохранить существующий порядок обработки событий, выполнение команд и JSON-представление UI.

**Non-Goals:**

- Не менять HTTP-протокол, Android-клиент, формы UI-событий или Claude streaming.
- Не менять реализацию `Runtime` и не вводить новый слой effect-интерпретации.
- Не дробить экранные компоненты на отдельные файлы: одного `home_components.ml` достаточно для текущего размера.

## Decisions

### Перенести `Cmd` в `Components`

`Components` становится местом для базовых Elm-примитивов: UI-дерева и команды. `Cmd` сохраняет текущую параметризацию по сообщению и операции `none`, `run` и `map`.

Это позволяет `Home_components` использовать `Cmd` через `open Components`, не импортируя `Home`. Вариант оставить `Cmd` в `Home` создал бы обратную зависимость `Home_components -> Home` при том, что `Home` должен импортировать `Home_components`.

### Перенести компоненты целиком в `Home_components`

`Home_components` содержит модули `Worktrees`, `New_worktree` и `Worktree` вместе с их состоянием, сообщениями, view-функциями, командами и update-функциями. `Worktrees` сохраняет непосредственный вызов `Runtime.load_worktrees` и переносит `root ()`, так как это существующая реализация его команды загрузки.

Компоненты не зависят от `Home`; `Home` импортирует их и оборачивает дочерние сообщения в свой `Home.msg`. Это сохраняет текущий `Cmd.map` как механизм подъёма команд в корневое сообщение.

Вариант вынести только `view` сделал бы компоненты presentation-only и заставил бы `Home` владеть их `Cmd`, что противоречит выбранной границе самостоятельных Elm-компонентов.

### Оставить `Home` корневым компоновщиком и серверным мостом

`Home` сохраняет типы `screen`, `state` и корневого `msg`, переходы между экранами, lift-функции, `Atomic`-состояние, JSON-декодирование и функции для Claude stream. При рендеринге он вызывает `Home_components.*.view`; при обработке дочернего сообщения он вызывает соответствующий `update` и отображает `Cmd` в `Home.msg`.

Так сохраняется однонаправленный граф зависимостей:

```text
Components -> Home_components -> Home -> Server
Runtime ----------------------> Home_components
Runtime ---------------------------------> Server
```

## Risks / Trade-offs

- [Изменение расположения модулей ломает внутренние ссылки тестов] → Обновить тесты на `Home_components` и `Components.Cmd` в том же изменении.
- [Механический перенос меняет сериализованный UI или event-тип] → Сохранить определения типов и тела `view`/`update` без семантических изменений и выполнить существующие тесты.
- [`root ()` остаётся связанной с аргументами процесса деталью в компоненте списка] → Не расширять рефакторинг внедрением зависимостей; выделить это отдельно только при появлении другой точки запуска.

## Migration Plan

1. Перенести `Cmd` в `Components`.
2. Создать `Home_components` и перенести три текущих компонентных модуля вместе с нужным `root ()`.
3. Переподключить `Home` к новым модулям и сохранить подъём команд через `Components.Cmd.map`.
4. Обновить тестовые ссылки на новые публичные пути модулей, отформатировать OCaml-файлы и запустить `dune test`.

Откат выполняется возвратом рефакторингового изменения: формат протокола и данные не мигрируют.
