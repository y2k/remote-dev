## Context

См. `proposal.md` для мотивации. Каждый модуль в `Home_components` уже имеет `model`, `view` и `update`, но начальное состояние разделено между `initial` и `enter`; в `Home` поверх этого существуют ещё три функции `enter_*`, которые одновременно выбирают экран, создают дочернюю модель и поднимают команду.

`Cmd` поддерживает одну команду, поэтому текущий bootstrap намеренно последователен: сначала загружаются эмуляторы, затем список worktree. Рефакторинг должен сохранить этот порядок и не менять сериализуемые `msg`.

## Goals / Non-Goals

**Goals:**
- Дать каждому stateful-компоненту узнаваемый TEA-контракт `init`, `view`, `update`.
- Оставить выбор следующего `screen` в единственной функции переходов `Home.update`.
- Сохранить модели, команды и результаты всех существующих переходов.

**Non-Goals:**
- Не менять типы `model`, `screen` и `msg` или JSON-кодирование сообщений.
- Не расширять `Cmd`, не запускать bootstrap-команды параллельно и не добавлять отдельный router.
- Не объединять компоненты и не перерабатывать общий helper `update_page`.

## Decisions

### Заменить `initial` и `enter` одним `init`

Каждый модуль `New_worktree`, `Emulator`, `Worktree` и `Worktrees` получит `init` с текущими аргументами соответствующего `enter` и результатом `model * msg Cmd.t`. Текущая модель и текущая стартовая команда переходят в `init` без изменения.

Отдельный `initial` не сохраняется: иначе остаются два API и прежняя неоднозначность, какой из них является началом TEA-компонента. Местам, которым нужна только чистая начальная модель, достаточно взять первый элемент результата `init`; создание значения `Cmd` не выполняет эффект.

Альтернатива — только переименовать `enter` и оставить `initial` — даёт меньший diff, но сохраняет дублирующий lifecycle-контракт и не решает исходную проблему полностью.

### Выполнять переходы непосредственно в `Home.update`

В ветках `Initialize_emulator`, `Back`, `Worktrees.Select` и `Worktrees.Open_creation` `Home.update` вызывает `init` целевого компонента, помещает модель в соответствующий вариант `screen` и поднимает команду через существующий `lift_*`. Благодаря этому вход в экран остаётся обычным результатом `update`, а `enter_worktrees`, `enter_worktree` и `enter_new_worktree` удаляются.

Не вводится отдельный navigation message или таблица переходов: текущие child messages уже однозначно задают переход, а дополнительный слой только перенесёт те же ветки из одного места в другое.

### Сохранить последовательный bootstrap

`Home.init` создаёт стартовые модели через child `init`, запускает только команду `Emulator.init` и сохраняет текущий `Initialize_emulator`. После её обработки `Home.update` повторно получает модель и команду `Worktrees.init` и запускает загрузку worktree, как сейчас.

Альтернатива с `Cmd.batch` потребовала бы менять command runtime и порядок документов ради задачи, которая этого не требует.

## Risks / Trade-offs

- [Вызов `init` для получения только модели создаёт неисполняемую команду] → `Cmd` является чистым значением; тестами зафиксировать, что эффект начинается только через `Cmd.run`.
- [Ручное раскрытие трёх переходов добавит похожие строки в `Home.update`] → оставить их рядом с соответствующими message-ветками; не вводить абстракцию для трёх разных конструкторов экрана.
- [Change `dispatch-input-handlers` изменит те же файлы и тесты] → реализовывать поверх его актуального состояния либо разрешить конфликты до запуска общей проверки.

## Migration Plan

1. Заменить component API и перевести `Home` и серверное начальное состояние на `init`.
2. Перевести навигационные ветки `Home.update`, затем удалить все `enter` и `enter_*`.
3. Обновить прямые вызовы в проверках и запустить OCaml test suite.

Откат состоит в возврате прежних имён и helpers; миграции данных или совместимости протокола нет.
