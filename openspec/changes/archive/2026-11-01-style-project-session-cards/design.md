# Design

## Context

Мотивация и согласованная область — `proposal.md`. `Directories.view` сейчас создаёт кнопки; `Sessions.view` — колонку с `surface`, обводкой 1 dp, радиусом 12 dp, отступом 16 dp и кнопкой-заголовком. В `Components` и Android нет кликабельного контейнера или роли приглушённого текста. Существующая типографика `body`, `heading`, `caption`, `code` используется также вне списков.

Экраны Stitch используют `surface-container-low`, радиус/отступ 12 px и интервалы 8 px. В `Theme.kt` уже определены `surfaceContainerLow` (`#181C20` / `#F5F7FA`) и `onSurfaceVariant` (`#C3C6D6` / `#616C75`). Точные значения экранов получены из HTML; это не измерения JPEG. Светлая тема использует существующие роли приложения, поскольку проверенные экраны показывают тёмный вариант.

## Goals / Non-Goals

**Goals:**
- Один небольшой семантический примитив для согласованной карточки, применимый в существующем дереве UI.
- Сохранить TEA: данные и события выбираются чистыми backend-представлениями; Android отвечает за отрисовку и стандартное взаимодействие.
- Локализовать новую типографику, чтобы не менять размеры и цвета текста чата и других экранов.

**Non-Goals:**
- Конструктор произвольных кликабельных поверхностей, настраиваемых теней или новая система тем.
- Изменения моделей загрузки, маршрутизации, данных OpenCode, общего соотношения панелей и настроек шрифтов.

## Decisions

### Approaches: семантический узел card

Предлагаемое техническое решение: добавить в `lib/components.ml` вариант `Card` с обязательным событием и списком дочерних узлов, конструктор `card ~event children`, рекурсивные `map` и `to_json`. Wire-форма: `{"@type":"card","event":[...],"children":[...]}`. В `MainActivity.kt` добавить соответствующий `UiNode.Card` и строгий разбор массивов. Новые поля внешнего вида не нужны.

Альтернатива — расширять row/column кликом, тенью и новыми цветовыми ролями — потребовала бы больше универсальных параметров и правил их совместимости ради одного согласованного оформления. Альтернатива с распознаванием названий или событий на Android нарушает серверный выбор представления. Поэтому выбран фиксированный семантический примитив; это инженерный выбор плана, а не отдельное пожелание пользователя.

### Compose и взаимодействие

В `UiNodeContent.kt` использовать стандартный кликабельный Material Card/Surface с явно заданными `surfaceContainerLow`, радиусом 12 dp, нулевой tonal elevation и лёгкой shadow elevation 1 dp. Это предотвращает неожиданную тонировку фона. Содержимое — вертикальная колонка с отступом 12 dp и промежутками 2 dp, отрисовывающая дочерние узлы существующим рендерером. Карточка занимает доступную ширину, минимум 48 dp по высоте и растёт по содержимому.

Стандартный clickable обеспечивает ripple, клавиатуру, accessibility и отмену нажатия при прокрутке. Объединить семантику текстовых детей в одну доступную карточку. `enabled = !eventInProgress`, отправка через существующий `onButtonEvent`, с `value: null`; новая очередь или gesture detector не нужны. Списки создают только текстовых детей, без вложенных действий.

Тень 1 dp, внутренний промежуток 2 dp, минимальная высота 48 dp и нулевой tracking — конкретизации плана: лёгкая нативная тень, расстояние между текстом из Sessions HTML и стандартный размер цели нажатия. Они не копируют CSS-тень буквально.

### Текстовые роли

Расширить семантические стили тремя значениями: `projectTitle` — 17/22 sp, 500; `sessionTitle` — 17/22 sp, 600; `cardMeta` — 12/18 sp, 400. Заголовки используют `onSurface`, metadata — `onSurfaceVariant`, tracking 0. Определения держать рядом с существующей типографикой в `ui/theme/Type.kt`; настройки уже используемых Material-стилей не переопределять ради карточек.

Сохранить системную семью, мягкий перенос, не задавать `maxLines`, ellipsis или фиксированную высоту. Не менять глобальные `Caption` и `Code`: иначе изменится чат. Альтернатива с произвольными size/weight/color в JSON даёт ненужный API для этой задачи.

### Композиция списков

В `Directories` заменить каждую кнопку карточкой с одним `projectTitle`, передавая тот же `Click (Filename.concat root name)`. В `Sessions` создать карточку из трёх строк: заголовок, directory, `Status: ...`; сохранить полный retry-текст и событие `Select session.id`. Вертикальная композиция предотвращает конкуренцию длинного статуса с заголовком за ширину.

У контейнеров списков задать gap 8 dp. Сохранить существующие внешние отступы, заголовки и weighted scrolling; создание сессии и progress остаются внутри того же scrolling child перед карточками. Обёртки событий с tab ID/generation сохраняются через `Components.map`. Отдельных моделей или update для статической карточки не требуется; компоненты `Directories`/`Sessions` остаются самодостаточными TEA-секциями.

## Risks / Trade-offs

- Новый узел неизвестен старому Android → сначала обновить клиент, затем backend; без версионирования или fallback для этой совместно развиваемой пары.
- Большая область нажатия может мешать scroll → проверить drag/cancel, блокировку повторной отправки, нажатие по padding и accessibility.
- Длинные retry-тексты увеличивают карточки → это согласованный выбор в пользу сохранения всей информации; проверить узкую панель и font scale 1.25.
- Общая `.stitch/DESIGN.md` и старые graphite-требования расходятся с экранами и текущей темой → источники явно указаны в proposal; delta определяет приоритет цветов именно карточек, без глобальной смены палитры.
- Известный baseline-сбой `emulatorPanelSurfaceFillsAllocationAndPreservesPreview` отслеживается в issue #3 → сообщать отдельно, не маскировать новым expected-цветом в этой задаче.

## Migration Plan

Миграции данных нет. Собрать и проверить новый Android-клиент, установить на устройство из корневой `.envrc`, затем запустить backend с новым wire-узлом. Новый клиент продолжает принимать старые документы. При откате сначала вернуть backend к прежним кнопкам/колонкам, затем при необходимости клиент.

Проверка включает backend serialization/event mapping, строгий Android parser, клики по поверхности и scroll, цвета/геометрию обеих тем, длинные строки при 125% масштабе. Host-проверки выполняются независимо от доступности устройства; device-проверки используют только `ANDROID_SERIAL` из корневой `.envrc`. После визуальной проверки восстановить исходную тему и масштаб.
