## Context

См. `proposal.md` для мотивации. `Worktrees` и `Worktree` уже инкапсулируют свои `model`, `msg`, `update`, `action` и команды. `Home` хранит активный `screen`, поднимает page-команды через `Cmd.map` и обрабатывает переходы между экранами. Только транспортный `decode` ещё создаёт плоские варианты `Home.msg`, которые `Home.update` сразу преобразует обратно в page-сообщения.

## Goals / Non-Goals

**Goals:**

- Сохранить существующую обработку объявленных UI-событий, переходов экранов, команд и ошибок.
- Сделать вложенные page-сообщения единственным путём доставки page-событий в `Home.update`.
- Оставить типы страниц явными и проверяемыми компилятором.

**Non-Goals:**

- Не обобщать страницы через first-class modules, GADT или новый `Page` интерфейс.
- Не менять JSON event envelope, UI-компоненты, HTTP-маршрут или модель состояния.
- Не добавлять новые события, экраны или асинхронную модель команд.

## Decisions

`Home.msg` будет содержать `Worktrees_msg of Worktrees.msg` и `Worktree_msg of Worktree.msg` вместо плоских вариантов `Select_worktree` и `Run_claude`. `decode` сразу создаёт эти вложенные варианты для опубликованных page-событий. Это соответствует Elm-паттерну, в котором дочерняя страница получает свой `Msg`, а контейнер поднимает команды обратно через `Cmd.map`.

`Load` и `Error` останутся корневыми сообщениями. `Load` исходит от системного refresh клиента и имеет существующую экранно-зависимую семантику; `Error` является результатом transport decoding, а не действием страницы. Их маршрутизация останется в `Home` и сохранит текущий результат для каждого активного экрана.

`update_worktrees` и `update_worktree` останутся отдельными адаптерами. Они различаются реальным поведением: первый обрабатывает `Open path`, второй возвращает к загруженному списку после `Back_to_worktrees`; оба применяют свой конструктор при `Cmd.map`. Общий `Page` abstraction потребовал бы скрыть несовместимые `model`, `msg` и `action` без уменьшения этой логики, поэтому он отклонён.

Для page-сообщения неактивного экрана `Home` сохранит текущую защитную обработку ошибки в активной модели. Объявленные текущим документом события всегда маршрутизируются в активную страницу; эта ветка остаётся только для прямого или некорректного transport-вызова и не является новым протокольным поведением.

## Risks / Trade-offs

- [Транспортная строка события и конструктор page-сообщения остаются в разных местах] → Для текущих четырёх событий это минимальный явный mapping; общий сериализуемый event framework не вводится.
- [Неподходящее page-сообщение всё ещё возможно создать внутри OCaml] → `Home.update` сохраняет обработку ошибки вместо молчаливого игнорирования, поэтому сервер не получает неявный no-op.
- [Добавление экрана потребует ещё одного вложенного варианта и маршрута] → Это ожидаемая явная точка интеграции; абстракцию следует рассматривать только после появления повторяемой структуры у нескольких новых экранов.
