## Context

См. motivation в `proposal.md`. Сейчас initial модель создаётся напрямую, а `Worktrees.enter` с командой загрузки вызывается только при переходе назад. `dispatch` немедленно выполняет `Cmd` и возвращает только финальную модель. HTTP response для Claude уже остаётся открытым и передаёт несколько UI-документов, но остальные requests с command не показывают промежуточную модель.

## Goals / Non-Goals

**Goals:**

- Сделать `Home.init : unit -> model * Cmd msg` единственной точкой входа initial lifecycle и выполнять его до открытия HTTP endpoint.
- Передать модель до и после обычной команды, запущенной UI-событием, в одном HTTP response.
- Сохранить JSON envelope для пользовательских `POST` events и текущий Claude stream.

**Non-Goals:**

- Не добавлять SSE, WebSocket, polling, persistence или поддержку нескольких клиентов.
- Не делать `Cmd` конкурентным или многошаговым: текущая команда синхронно создаёт не более одного сообщения.
- Не менять семантику ручного `load` как пользовательского refresh.

## Decisions

### Инициализировать приложение при старте сервера

`Home.init` остаётся чистой функцией и возвращает initial model с command. Перед началом приёма соединений server runtime сохраняет эту модель, выполняет command, применяет его message и только затем начинает слушать endpoint. Поэтому `GET /` всегда возвращает текущий готовый UI-document одним JSON response.

Это исключает отдельный lifecycle marker и не перезапускает приложение при повторных `GET`. Инициализация при первом `GET` отклонена: она требует отличать ещё неинициализированную модель от корректного пустого списка worktree.

### Интерпретировать `Cmd` в HTTP responder, не в `dispatch`

Выделяется один шаг обработки, возвращающий model и optional `Cmd`. Обычный JSON responder использует его для событий без команды. Streaming responder сначала записывает document модели после `update`, затем выполняет command, применяет полученное message и записывает следующий document. Ошибка команды остаётся данными UI-модели, а не меняет HTTP status.

Текущий рекурсивный `dispatch`, который немедленно схлопывает команду и её результат в один document, отклонён, поскольку он не оставляет промежуточную модель доступной transport layer.

### Выбирать response format по наличию обычной команды

`POST` events, создающие обычную command, получают `application/x-ndjson`. `GET /` и события без command сохраняют `application/json`. Успешный `run_claude` сохраняет специальный NDJSON producer дельт; это не ordinary UI command lifecycle.

Единый NDJSON для всех UI responses отклонён: он меняет формат простых синхронных действий без потребности.

### Разобрать NDJSON в Android как общий response format

Клиент выбирает parser по `Content-Type`, а не по event type. Для NDJSON он применяет каждый полный document в порядке поступления и считает запрос завершённым только после закрытия response. Это переиспользует существующую обработку Claude stream для навигационных commands.

## Risks / Trade-offs

- [Запуск сервера удерживается до завершения `git worktree list`] → это локальная синхронная команда; при необходимости неблокирующего запуска потребуется отдельное изменение transport runtime.
- [Повторный `GET /` не делает refresh] → явный `load` остаётся существующим пользовательским refresh event.
- [Поток содержит только два документа для обычной команды] → это соответствует текущему `Cmd`; перейти к асинхронным или множественным результатам можно отдельным изменением transport runtime.

## Migration Plan

1. Сервер выполняет initial lifecycle до начала приёма соединений и возвращает текущий document на `GET /`.
2. Android заменяет initial `POST load` на `GET` и обобщает NDJSON parser для event responses.
3. Документация и protocol tests обновляются одновременно с клиентом и сервером.
4. При откате клиент возвращается к initial `POST load`, а сервер к прежнему single-document contract.
