## Context

Мотивация и согласованный объём описаны в `proposal.md`. Сейчас `Home.init` выбирает `Worktrees`, `Worktree.model` хранит только текущий ответ и session ID, а `Runtime.claude_process` запускает `--print`/`--resume`. `Server.respond` связывает NDJSON response с длительностью этого процесса. Android удерживает `eventInProgress` до закрытия response, поэтому такой транспорт нельзя использовать для наблюдения за внешним агентом: он заблокирует сообщения, разрешения и Back.

Проверены исходники `lib/{home,home_components,runtime,server}.ml`, клиент `MainActivity.kt`, README и существующие тесты режимов, списка и запуска CLI. Старые спецификации прямо требуют создания разговора после выбора worktree; delta-specs снимают эти требования, а не оставляют два противоречащих друг другу сценария.

## Goals / Non-Goals

**Goals:** сохранить backend-defined UI с TEA, отдельно получать события внешней сессии и обрабатывать пользовательские действия; использовать только опубликованные контракты Claude; до основной реализации доказать совместимость нужных механизмов.

**Non-Goals:** эмулятор терминала, доступ к внутреннему supervisor Claude, управление жизненным циклом агента, собственный архив разговоров, универсальный framework провайдеров, точное копирование всех элементов интерфейса Claude.

## Decisions

### 1. Проверка осуществимости — обязательный первый этап

Это проект условной реализации, а не заявление о готовом API подключения. Пользователь согласовал эксперимент перед основной реализацией. Создание этого плана не разрешает запуск эксперимента в explore mode: для выполнения нужен отдельный переход к реализации и согласованный запуск изолированных тестовых сессий. Рабочие агенты пользователя не используются как испытательный стенд.

Проверить на установленной версии Claude:

| Проверка | Критерий продолжения |
| --- | --- |
| Подключение собственного channel | Поддерживаемая регистрация stdio MCP, доставка и `reply` без запуска второго разговора |
| Идентичность | Две сессии в одной директории не смешиваются; resume/clear и переход в фон не оставляют ложную доступность чата |
| История и живой текст | Сообщения из терминала и приложения видны в правильном порядке; переход от промежуточного к сохранённому ответу без дублей и потерь |
| Занятый агент | Сообщение доходит на последующем ходе; интерфейс не объявляет неподтверждённую обработку |
| Разрешения и вопросы | Ответ относится к конкретному ожидающему запросу; поздний ответ не одобряет следующее действие; локальный ответ корректно закрывает удалённый запрос |
| Обрыв | Отображённый текст сохраняется, отправка блокируется, автоматического повтора или resume нет |
| Доступ отправителя | Посторонний клиент не может отправить сообщение или ответить на разрешение |

Если любой обязательный сценарий не реализуется публичными интерфейсами, основная реализация блокируется. Зафиксировать факт и вернуться к пользователю; не заменять историю только channel-ответами и не использовать внутренний протокол как fallback.

#### Результат первого эксперимента — 2026-09-09

**Статус: BLOCKED на задаче 1.1.** Пользователь разрешил временный стенд и тестовые сессии. Установлена Claude Code **2.1.266**, интерактивный запуск отображает **Claude Team**. Успешная регистрация channel не подтверждена, поэтому задача 1.1 и последующие задачи остаются невыполненными.

Временный стенд: `/var/folders/yn/rfk_wf_941g9wdgstvd2g1_80000gn/T/opencode/claude-agent-chat-spike/`. Файлы `probe.py`, `mcp.json`, `settings.json`, `command.json`, `result.txt`, `events.jsonl`, `registration-debug.log` содержат локальный тест и свидетельства; это временные файлы, не часть поставки приложения. Минимальный Python stdlib bridge использован только для первичной проверки регистрации публичного wire protocol, не как решение для основной реализации.

Наблюдения:

1. Два коротких `--print` запуска с отдельными `--mcp-config`, `--settings`, `--strict-mcp-config`, `--restricted`, отключёнными built-in tools и лимитом `--max-budget-usd 0.05` завершили обычный prompt `READY`. Bridge получил `CLAUDE_CODE_SESSION_ID` соответствующей тестовой сессии.
2. Во втором запуске bridge отправил один `notifications/claude/channel` с просьбой ответить тестовым маркером. Маркер в ответе не появился. Само отсутствие ответа не использовано как доказательство политики: успешное MCP-соединение не доказывает регистрацию канала.
3. Отдельный интерактивный запуск через PTY с `--ax-screen-reader` после подтверждения доверия только временной директории явно сообщил:


   Этот же запуск показал `server:probe · no MCP server configured with that name`; после снятия policy-блокера отдельно проверить интерактивное разрешение MCP-конфигурации. Не считать headless MCP handshake подтверждением интерактивной регистрации.
4. Тестовые процессы завершены; проверка `pgrep -fl "remote-dev-channel-probe|claude-agent-chat-spike/probe.py"` не нашла оставшихся процессов. История тестовых `--print` разговоров может сохраняться штатным Claude. Доверие временной директории подтверждалось через штатный локальный диалог; настройки политики не изменялись.

**Условие продолжения:** администратор разрешает Channels поддерживаемым способом, после чего повторяется задача 1.1. Пока этого нет, проверка доставки, native OCaml bridge, hooks, истории, разрешений и вопросов не выполняется; разделы 2–5 задач заблокированы. Development-флаг не обходил и не должен обходить запрет организации. Это блокер текущего окружения, не доказательство невозможности публичной интеграции вообще.

**Последующее решение пользователя:** «админы точно не разрешат». Условие продолжения текущего Channels-дизайна недоступно; работа отложена до выбора альтернативы. SDK-запуск, явный resume-handoff, терминальное подключение и read-only просмотр только обсуждались, ни один вариант не принят. Контекст и следующий вопрос сохранены в `handoff.md`. Следующие разделы описывают заблокированный план, а не разрешение продолжать его реализацию.

### 2. Обнаружение отдельно от доступности чата

Загружать `claude agents --json` через существующую границу выполнения команд; имя программы разрешать через локальный PATH. Без `--cwd`, без `--all`. Сохранять различие background `id`, conversation `sessionId` и PID; отсутствующие необязательные поля не заполнять выдуманными значениями. Результат команды определяет состав списка, поэтому working/blocked background record без живого PID может оставаться видимым, но не становится подключённым автоматически.

Chat eligibility требует действующего зарегистрированного channel и точного совпадения текущей сессии. Ни cwd, ни имя не служат ключом. CLI failure отображается в текущей модели как ошибка, не как пустой успешный список.

Предлагаемый совместимый default для старого positional root: продолжать принимать его, но не использовать как фильтр или cwd разговора. Это не требует ломать существующие команды запуска; README объясняет новую семантику.

### 3. Публичный channel bridge и hooks

```text
Android UI <--> OCaml backend / TEA
                       |
                       +-- claude agents --json
                       |
                       +-- local bridge <--> stdio MCP <--> enrolled Claude
                       |
                       +-- hook events <-- Claude
                       |
                       +-- supported history reader
```

Claude запускает stdio MCP server при своей явной настройке. Bridge передаёт `notifications/claude/channel`, предоставляет `reply` и обрабатывает permission relay. Он не запускает Claude. Пользователь на компьютере выполняет настройку и запуск с флагом подключения; приложение не редактирует настройки Claude автоматически.

Проверяемый минимальный вариант — небольшой bridge на OCaml с newline-delimited JSON-RPC, существующими JSON/HTTP средствами, без полноценного Agent SDK runtime. Публичный MCP wire format не требует конкретного языка, но channel guide ориентирован на TypeScript SDK: совместимость OCaml сначала доказать. Если обязательна иная зависимость, отразить результат до основной реализации, не писать собственный общий MCP framework.

`CLAUDE_CODE_SESSION_ID` доступен stdio MCP subprocess, но после `/clear` или некоторых resume-сценариев может устареть. Hook payload содержит текущий `session_id`. Проверить сопоставление через идентификатор экземпляра интеграции, переданный при запуске обоим участникам. При неоднозначности блокировать отправку, не угадывать целевой разговор.

Локальный ingress bridge/hooks не следует бездумно добавлять на публичный LAN endpoint `/`: принимать его через отдельную локальную границу и проверять принадлежность подключения. Удалённые сообщения и разрешения требуют аутентифицированного клиента; минимальную схему привязки единственного Android-клиента к backend и защиты локальной регистрации проверить в первом этапе. Наличие устройства в LAN само по себе не подтверждает отправителя. Это требование trust boundary, не проект многопользовательских аккаунтов.

### 4. История и текущий ответ — разные источники

Публичные SDK `getSessionMessages` читают сохранённую историю. Hook `MessageDisplay` отдаёт промежуточный assistant text, но его `message_id` нельзя считать ID сообщения transcript. Нельзя склеивать эти источники только по равенству текста: одинаковые ответы допустимы.

В эксперименте определить поддерживаемый reader истории и границу замены промежуточного ответа завершёнными сообщениями. Предпочесть доступный публичный reader, а не недокументированный парсер JSONL. Если reader требует отдельного runtime, сначала зафиксировать необходимую минимальную зависимость. Не создавать собственную постоянную копию истории: Claude остаётся её владельцем; модель держит отображаемую историю, промежуточный текст и пользовательский ввод.

Channel `reply` — средство доставки ответа, не гарантия полной истории. Проверить, как channel prompt представлен в сохранённых сообщениях и какие hooks на него срабатывают; одна логическая реплика не должна появляться дважды. Полные tool inputs нужны для конкретного permission/question UI, но не добавляются как подробный журнал инструментов.

### 5. TEA и конечное обновление UI

В `home_components.ml` добавить самодостаточные Claude-компоненты списка и чата с `model`, `msg`, чистым `view`, `update`; переиспользовать существующие элементы, `Cmd` и образец OpenCode session screens. Отдельные компоненты для pending input и доставки допустимы в том же файле. Не обобщать заранее провайдеры.

Предлагаемый простой транспорт Android — периодическое получение текущего полного UI-документа конечным запросом, пока открыт Claude chat. Hooks обновляют подтверждённую серверную модель независимо от этого запроса. Сохраняется `POST /` для действий и конечных команд; не удерживать submit response до конца хода Claude. Фоновое чтение не должно перетирать более новое действие или возвращать пользователя на прежний экран: сериализовать короткие операции либо отбрасывать устаревший результат по поколению экрана. Конкретный интервал выбрать после проверки; не добавлять настройку без необходимости.

Это проще нового постоянного WebSocket и сохраняет контракт полных backend-defined документов. Если измерения не позволяют обеспечить обновления до окончания длинного ответа, пересмотреть транспорт, сохранив разделение наблюдения и действий. Не менять OpenCode refresh/stop и обновление изображений эмулятора.

### 6. Доставка, вопросы и потеря соединения

Channel notification не имеет acknowledgment. Хранить текст отправки и только наблюдаемые стадии: до передачи, передано в канал/ожидает обработки, неопределённая доставка или явная ошибка. Не объявлять `delivered`/`processed` по успешной записи stdio и не обещать exactly-once. Автоматический resend отсутствует; повтор — отдельное действие пользователя.

Permission relay связывает `request_id` с сессией и подключением. При локальном решении, закрытии запроса или смене сессии старый UI не может разрешить новое действие. `AskUserQuestion` проверяется через опубликованный hook с `updatedInput`; это отдельный контракт, его нельзя подменить permission verdict. Доверие проекту и MCP consent остаются локальными. Никаких `dangerously-skip-permissions`.

При разрыве каналов оставлять отображённую историю и draft, снимать доступность отправки и ответов на pending requests до надёжного восстановления их актуальности. При восстановлении можно перечитать данные, но нельзя повторять сообщения или запускать/resume агента. Back перечитывает активный список; завершённый агент исчезает согласно discovery.

## Risks / Trade-offs

- Channels остаются research preview и зависят от политики → фиксировать проверенную версию и необходимые публичные флаги в инструкции подключения; policy denial показывать явно, не обходить.
- История, hooks и channel replies не образуют готовую единую шину → обязательная проверка сходимости до удаления рабочего Claude-сценария.
- Неподтверждаемая доставка → честное состояние неопределённости и ручной повтор; отсутствие собственного долговечного outbox намеренно.
- Текущий LAN HTTP клиент не задаёт достаточный контракт авторизации approvals → проверка минимальной привязки и защиты отправителя блокирует удалённые управляющие действия до её прохождения.
- `--clear`/resume/background могут менять идентичность или окружение → проверять жизненный цикл; отключать неоднозначное подключение вместо маршрутизации по cwd.
- Периодическое чтение добавляет небольшую задержку → получать промежуточные обновления без ожидания завершения хода; не обещать токен-в-токен отображение.

## Migration Plan

1. В отдельной реализации выполнить воспроизводимый эксперимент на тестовых сессиях; записать версию, результаты и минимальные необходимые зависимости в этот design. Непрошедший обязательный сценарий останавливает следующие этапы.
2. После успешной проверки реализовать интеграцию, TEA-экраны и конечное обновление клиента; заменить связанные тесты и обновить README. Не удалять рабочий путь до прохождения проверки.
3. Пользователь подключает Claude на компьютере и запускает сессии. Существующие неподключённые агенты сразу видны, но недоступны для чата.
4. Удалить worktree-specific UI, shortcuts и prompt-spawning путь, включая старые события. Не менять файлы worktrees или Claude history. Удаляемые requirements перечислены в delta-specs.
5. Откат приложения выполняется возвратом к предыдущей сборке; пользователь отключает настроенный channel/hooks отдельно. Ни миграции истории, ни удаления директорий не требуется.
